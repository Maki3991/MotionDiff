## 一、已经明确的事情，不需要团队重复回答

根据本次用户要求，下一轮的目标方向是：

1. 输入两个视频：教练／参考动作视频 A，学员动作视频 B。两段视频都有可明确选择的输入位置。
2. 两段视频都使用 MediaPipe 提取姿态数据。另一个对话正在进行的引擎测试，其实际结果届时读取，不在本文预设速度或精度结论。
3. 比较模块处理两份动作数据，输出差异及能够支持的改进提示。报告需要让普通使用者理解。
4. 开发者负责选择数据结构、归一化方式、时间对齐、差异指标、质量筛选和测试方法。团队不用回答这些专业问题。
5. 交付目标是能够实际运行的应用，包含两个视频输入、处理进度和结果展示。
6. 现有项目约定首版只支持一种明确的动作及一个动作片段。具体动作仍需团队决定；多运动目录不代表全部动作已经支持。

当前工作区的 PRD、DECISIONS 仍有“引擎待定”“预置参考视频＋现场录制”等早期表述。本文明确记录本轮的新方向为“两段视频输入＋MediaPipe”。进入开发 Goal 时，应依据本轮要求和团队填写结果同步这些文档，避免并存矛盾要求。

## 六、交给开发者决定并负责验证的事情

这些内容不放入团队选择题。开发者需要记录方案和证据，遇到效果不佳时主动调整。

| 开发者负责 | 应交付的可检查结果 |
| --- | --- |
| 视频如何转成数据、数据保存成什么格式 | 可重算的两份姿态序列，含原始帧号、时间、语义关节名称、坐标与质量信息；缺失点不冒充有效坐标 |
| 如何适配 MediaPipe | 使用已有导出器时先核对实际行为；保留原生可靠性字段，不直接套用 OpenPose 的置信度门槛 |
| 如何减少画面位置、人物大小和动作速度差异的影响 | 在约定拍摄范围内，用实际素材比较处理前后的结果，并保留限制说明 |
| 比哪些位置、角度、时段以及如何汇总 | 结合第 1、4、6 题选方法；每条主要差异能回到对应的两段画面及可解释的指标 |
| 是否采用抽帧来提速 | 先读取另一对话的全帧测试结果；只有实际验证仍保留所需差异时才采用抽帧，并记录原始时间，不让团队选择技术参数 |
| 应用使用什么框架、如何启动和保存结果 | 能按说明从当前环境启动，输入两个视频并得到结果；进度、错误和重试状态可见 |
| 如何把差异写成建议 | 以数据和第 4 题约定的依据为基础生成表述；没有证据的地方不生成确定性的纠错结论 |
| 如何证明完成 | 自动检查与真实视频运行证据、耗时记录、报告示例、已知失败情况和复现步骤 |

实现现状以实际代码和运行证据为准。本文对责任的分配不代表这些功能已经存在。

## 八、填写之后，下一轮 Goal 可以这样设置

以下是待填的目标模板；方括号中的产品条件来自问卷，不要求团队补技术方案。

> 在现有 MotionDiff 项目基础上，实现并实际运行一个两视频动作比较应用。使用位置为［第 5 题］，首个支持动作是［第 1 题］，按［第 2 题］的参与者范围和［第 3 题］的拍摄条件进行验证。
>
> 使用者选择一段教练／参考视频和一段学员视频后，程序使用 MediaPipe 处理两段视频，保存可追查的动作数据。由你负责设计并实现数据适配、质量筛选、动作对齐和差异分析，依据［第 4 题］生成带画面证据的差异与改进提示，并在可用界面中展示。
>
> 按［第 6 题］验收，并遵守第 7～10 题及资源边界。对识别不足、片段不可比或超出支持范围的输入，给出清楚的状态与下一步操作。提供启动命令、实际运行结果、耗时、报告样例及已知限制。需要新测试素材时明确所缺条件，并继续完成不依赖该素材的工作。
>
> 先同步团队已确定的要求到 PRD、DECISIONS 和验收文档，再按可运行的小阶段交付；最终完成以实际验收证据为准。算法和工程选择由你自主处理并说明依据，不再要求团队选择专业技术名词。

### 给开发者的最低完成检查

- [ ] 从启动说明进入可用应用，两段视频的角色明确，普通使用者无需手动整理 JSON。
- [ ] 两段视频经 MediaPipe 实际处理，保存必要的数据来源、时间和质量信息。
- [ ] 比较逻辑真实消费这两份数据，报告不是固定文案或预先硬编码的结论。
- [ ] 主要差异能定位到两段视频的对应片段、人体侧别及相关部位。
- [ ] 相对参考的提示或经确认的规范性提示，符合第 4 题的依据范围。
- [ ] 无人、关键部位不可见、输入无效和不可比较等情况有可理解的结果。
- [ ] 第 6 题要求的样例得到实际验证；未完成的覆盖范围不写成已经支持。
- [ ] 计时符合第 8 题约定口径；若有硬性能目标，使用约定长度的素材验证。
- [ ] 团队要求的使用方式与报告交付方式完成，现有素材和其他测试输出仍可追查。
